# AI Architecture Notes

The canonical architecture document is `ARCHITECTURE.md`. This file is its compact
executable-context mirror.

It does not own capability maturity. The bullets below state what each contract is and
what it connects to; none of them state whether a gate is Contract Verified, Integrated,
or Operational. Read maturity from `PROJECT_STATE.md` and the evidence behind it from
`docs/verification-log.md`.

A contract description here MUST state what the contract connects to, not only what it
is. A described-but-unconnected contract is how the `completion` conflict happened:
this file described each queue, runtime, and result contract correctly while omitting
the ordered connection backlog between them, so the missing middle transition was not
visible. `ARCHITECTURE.md` holds that backlog under Gate 8 Connection Sequence And
Completion Boundary, and Completion Semantics states the three distinct facts that
`completion` names.

Current direction:

- Development-session recovery uses one ignored machine-written checkpoint below
  `.enhancer/session-checkpoint/`, bound to the active task contract and a monotonic
  single-writer revision. It records only execution position, evidence references, and
  artifact identities; canonical documents, Git, and fresh verification retain their
  existing authority. Start/record/show/clear CLI operations support forced-stop resume,
  and clear requires a stable artifact-matched state.
- A multi-increment Active Task may carry one optional bounded `## Dynamic Workflow` in
  `CURRENT_TASK.md`: two through sixteen ordered increments, `Sequential` mode, stable
  identities, dependencies, state, scope, exit criteria, verification, next action, and
  explicit stop conditions. At most one increment is `In Progress`; only the first
  dependency-ready pending entry can advance after fresh evidence is read. The parent
  task remains the sole approval and scope envelope, the checkpoint remains execution
  position only, and dynamic selection grants no new Tool, external-action, parallel,
  background, or multi-agent authority.
- Adaptive development subagents are a host-session execution topology selected by the
  primary Agent inside the existing user request and Active Task. The bounded policy is
  read-only, uses at most three concurrent children and one delegation level, keeps the
  primary as sole mutation/evidence/lifecycle owner, and treats reports as
  recommendations. It is independent of Dynamic Workflow presence and is not Gate 13
  product/runtime multi-agent implementation or maturity.

- Enhancer is a self-hosting AI Development Operating System.
- Delivery Gate 0 Context, planning, Assisted Loop, repeated-loop safety, ToolResult, VerificationEvidence, and governance contracts are connected through an authority-preserving lifecycle test; the bounded read-only Tool, persisted evidence, Tool-driven Agent Loop, verification, and RunRecord boundaries compose into the first supported read-only CLI.
- Executable repository context loads the seven governed `.ai/` documents before the eight canonical root documents.
- The Planner follows the canonical Delivery Gate / Specified - Next grammar and is regression-tested against the actual Enhancer Roadmap.
- Capability maturity is Specified, Contract Verified, Integrated, Operational, or Released; do not use Implemented alone as a roadmap state.
- A cross-cutting Product Journey and Evaluation Track complements, but never replaces, Delivery Gates. Four initial journeys cover governed bug repair, bounded feature delivery, evidence-backed codebase explanation, and interrupted-run recovery; release evidence uses versioned fixtures, predeclared thresholds, explicit denominators, held-out regression checks, and immutable run/model/policy/revision/evaluator provenance.
- The evaluation harness measures task success, incorrect changes, retry/recovery, cost/time, user intervention, post-verification regression, and multi-agent delta. Multi-agent comparisons use the same fixture revision and comparable budget envelope as the single-agent baseline; confidence or cherry-picked demonstrations are not evidence.

Listing delegates ordering to `RunRecordStore.recentReferences`, resolves no record, and creates no missing root.
- Gate 0 integration proves planning -> explicit external activation -> verified Gate 5 execution and replay without automatic Proposal approval or a second production orchestrator.
- Delivery Gate 6 Workspace and Project Brain Foundation covers the snapshot, view, graph, query, projector, and collector sub-capabilities, and the production CLI `run` path composes the view and graph. Diagnostics, terminal-session, and active/selected-file observation moved to Gate 12 by the 2026-07-15 user-approved re-scope decision. The snapshot identity is not stored in the RunRecord; Gate 7 envelopes own cross-handoff identity.
- Delivery Gate 7 Event Bus and IPC Foundation covers a reference-only `MessageEnvelope`, a deterministic single-threaded `InProcessMessageBus`, and a transport-neutral `MessageTransport` boundary spanning bounded payloads, topic fan-out, single-consumer queues, idempotency, journal replay, failure isolation, bounded retry and dead-letter re-delivery, correlation cancellation, run-to-completion ordering, finite non-blocking backpressure, and hop-level transport acceptance without granting authority. A local spool adapter and its process-isolated work/result consumer exist; persistence beyond the per-hop spool, threading, durable/remote adapters, and supported messaging entry points remain deferred. The current `Specified - Next` gate is stated in `ROADMAP.md` and `PROJECT_STATE.md`, not here.
- Gate 7's connected work-message queue path: `WorkMessagePublisher` derives an envelope from a matching real approved task and Workspace snapshot, the in-process bus delivers/journals/replays it, and `WorkItemAdmissionHandler` retains it unchanged in Gate 8 admission without duplicate work. Process-isolated execution supplies a separate local `MessageTransport` work/result path with result causation and routes both decoded child Work execution and parent Result validation through fresh Message Bus queues before exposing their results. The Control producer/receiver connection persists a bound request before success and exposes storage failure through retry/dead-letter; Handoff, topic, and reliability branches outside those paths still lack a named real production connection.
- The bounded Control connection has separate supported producer and receiver commands. `scheduler-spool-control` reads an existing active/non-terminal Goal without runtime recovery, derives correlation/logical-run/causation only from its retained Work envelope, and publishes one untrusted intent through the file spool. `scheduler-receive-control` resolves the explicit pending or acknowledged point, validates its route and payload, publishes through the real Message Bus to `RuntimeControlAdmissionHandler`, and acknowledges only after the exact request is durable. Authenticated application remains Gate 12; durable journaling, directory consumption, and retention remain separate.
- Gate 8 durable work admission: `DurableWorkItemAdmissionHandler` is the separate persist-first consumer for the real work-message path. It applies a fixed bijective UUID domain transform so retry sees one stable WorkItem identity distinct from the message identity, creates dependency-free `QueuedWork`, and reports success only after `DurableSingleWorkerSchedulerQueue` persistence. Same-bus replay is suppressed; fresh-bus exact replay is a no-revision success, while changed content under the same identity fails closed.
- Gate 8 admission: immutable `WorkItem` admission retains one unchanged Gate 7 work envelope, adds a distinct canonical work identity and bounded required capability, and exposes approved task, snapshot, run, and Tool scope only as projections. It adds no runtime state, persistence, lease, or authority; the dependency-ready single-worker Scheduler queue is its first consumer.
- Gate 8's dependency-ready single-worker queue: immutable queued work carries up to 256 earlier-admitted dependency identities plus Scheduler-only `NORMAL`/`EXPEDITED` metadata, a run-scoped queue admits at most 4096 work items, ordinary selection is admission-ordered within each priority and releases only fully completed dependencies, and exactly one active slot exists. Recovery consumes one durable preferred identity before ordinary selection without changing fairness progress. The base queue creates no lease, failure policy, priority admission input, worker execution, or authority; the separate durable wrapper supplies schema-v3 state and restart recovery.
- Gate 8 durable queue state: one canonical queue identity, logical run, every exact ordered priority-bearing admission, maximum expedited burst, consecutive expedited progress, optional recovery preference, and the full status partition persist through a bounded schema-v3 integrity-checked atomic snapshot. Every update takes a stable queue-scoped non-blocking operating-system file lock across resolve, validation, and publication so cooperating local JVMs cannot overwrite the same prior revision; contention fails typed and the lock artifact carries no state or authority. Every new admission/claim/disposition persists before exposure; exact admission replay is revision-free, changed-content identity reuse fails closed, and restart recovery requeues interrupted active work with a one-shot exact preferred claim under explicit at-least-once semantics. Ordinary resolution rejects schema v2; the separate `scheduler-migrate-queue` maintenance boundary maps it losslessly to v3 through candidate validation, source-drift refusal, and atomic replacement. Schema v1, history compaction, distributed or broader cross-store coordination, leases/fences, external-effect deduplication, and parent-directory power-loss durability remain unsupported.
- Gate 8 queue inspection uses pure `SchedulerQueueStatus` over one directly resolved persisted snapshot: verified, failed, and active come from the queue partition, pending work is ready only when all dependencies are verified and blocked otherwise, every admission retains its exact priority, and maximum expedited burst, consecutive expedited progress, and the optional recovery preference remain observable. The separate bounded `scheduler-status` CLI reports an admission-ordered identity/state/priority prefix, reads no other store, and never recovers, creates, claims, consumes the preference, or updates the queue, so persisted selection state remains observation rather than a liveness or next-claim prediction.
- Gate 8 recovery inspection uses the single cycle checkpoint as its only cross-store anchor. `SchedulerRecoveryStatusReader` directly resolves one queue, optional checkpoint-named Goal, and optional checkpointed RunRecord, validates their exact WorkItem/result bindings, and accepts a projection only when bounded second reads observe the same queue revision, checkpoint value, and runtime revision. `scheduler-recovery-status` reports typed durable prefixes and `workerLiveness=UNKNOWN`; it never scans stores, evaluates lease expiry, invokes recovery, or mutates state. The stability check is sequential rather than an atomic multi-store snapshot.
- Gate 8 external-effect recovery inspection reuses that checkpoint-correlated Scheduler projection as its only Goal anchor. It point-resolves only the named Goal ledger, validates every effect against the runtime WorkItem and retained AgentRun history, integrity-checks each terminal Evidence Store binding without exposing content, and accepts output only after a bounded second Scheduler/ledger sample. Conservative aggregate precedence is `PREPARED`, user recovery, applied/deduplicated, then all compensated; a missing ledger is valid only before the Scheduler prefix advances beyond runtime recording. The separate bounded `scheduler-external-effect-status` surface never scans, creates, recovers, invokes, retries, compensates, or mutates state and makes no external-system claim beyond retained adapter evidence.
- Gate 8 invocation-spool recovery inspection reuses the checkpoint-correlated Scheduler Goal and AgentRun as its only filesystem anchor. It validates the private work/result spool against the exact runtime WorkItem and referenced RunRecord, rejects corrupt, foreign, symbolic, several-message, or changed bounded samples, and reports only bounded presence metadata through `scheduler-invocation-status`; it never scans, creates, consumes, launches, cleans, recovers, retries, or mutates a spool.
- Gate 8 durable submission: one immutable schema-v2 manifest binds the canonical message identity to the queue identity/capacity, required capability, exact work envelope, and `NORMAL`/`EXPEDITED` Scheduler priority before queue creation. `DurableWorkSubmissionService` resumes manifest -> queue -> exact priority-bearing admission prefixes without a mutable receipt; exact replay changes neither manifest nor queue revision, while changed content, changed priority, and capacity drift fail before admission mutation. Ordinary resolution rejects schema v1; the separate `scheduler-migrate-submission-manifest` maintenance boundary maps one stopped submission to v2 with `NORMAL` through candidate validation, source-drift refusal, and atomic replacement. Neither submission CLI yet accepts priority input.
- Gate 8 durable Goal/AgentRun lifecycle state: one schema-v4 Goal retains one exact WorkItem, an immutable ordered history of at most 16 distinctly identified AgentRuns, an attempt-bound retry-decision history, at most 256 exact lease-timeout records, and at most one authorization-bound cancellation application. `agentRun()` projects the latest attempt; ordinary result attempts advance through Planning, Ready, leased Executing, Awaiting Verification, and one typed terminal result. Verified completes, non-Verified parks at durable `RETRY_PENDING`, and matching authenticated cancellation terminally cancels current runtime state without becoming a completed attempt. Goal-wide fences and exact WorkItem, attempt, decision, control, cancellation, lease-timeout, and result prefixes persist before exposure; incompatible schema-v1-v3 runtime artifacts fail explicitly.
- Gate 8 fenced AgentRun ownership: `READY` acquisition issues a bounded single-owner lease with a persisted monotonic fence, injected time, and exclusive expiry; renew and execution completion require the current unexpired owner/fence, while restart or explicit reclaim at expiry durably returns execution to `READY` and makes the former owner stale. It grants no Tool authority and adds no worker, effect fencing, retry, multi-process lock, or clock-skew protocol.
- Gate 8 durable control requests: an active Goal/AgentRun may retain at most 256 exact `ControlPayload` envelopes bound to its work logical run, correlation, and causation. The ordered ledger is prefix-monotonic, persist-before-exposure, exact-replay idempotent across restart, and schema-v1 fail-closed for older payloads. It records untrusted intent only; Gate 12 still owns authenticated pause/resume/cancel application and no request changes runtime or Tool authority.
- Gate 8 durable external effects: one separate schema-v2 ledger per Goal retains at most 256 stable idempotency-keyed requests bound to the exact AgentRun, WorkItem, bounded adapter and operation identities, and semantic digest. The current unexpired owner/fence is required to persist evidence-free `PREPARED` and one evidence-bound terminal `APPLIED`, `DEDUPLICATED`, `COMPENSATED`, or `REQUIRES_USER_RECOVERY` outcome; exact replay is revision-free, history and evidence binding are monotonic, schema-v1 artifacts fail explicitly, and unresolved preparation never authorizes automatic replay. `DurableExternalEffectExecutor` composes the ledger with an `ExternalEffectAdapter` port and the Evidence Store: it validates identity and digest, persists `PREPARED` before one invocation, persists redacted complete evidence before terminal publication, resolves exact terminal replay without invocation, and refuses automatic execution from an already prepared record. A deterministic filesystem integration connects the real runtime lease, ledger, and Evidence Store; production external adapters remain Gate 11 work.
- Gate 8's corrected retry contract separates failed AgentRun attempts from terminal WorkItem disposition. A failed result stops at durable `RETRY_PENDING` while the queue item stays active; the exact Goal ledger and immutable attempt count produce a typed decision that persists before a checkpointed replacement attempt is appended or the Goal is terminally abandoned. Only an empty or all-`COMPENSATED` ledger admits automatic retry; `PREPARED`, `REQUIRES_USER_RECOVERY`, `APPLIED`, and `DEDUPLICATED` refuse until a cross-attempt adapter contract exists. The schema-v4 runtime retains exact AgentRun, decision, cancellation, and lease-timeout prefixes with Goal-wide fences; current implementation maturity remains owned by `PROJECT_STATE.md`.
- Gate 8's durable queue-to-lifecycle dispatch path: `DurableAgentRunDispatcher` uses an existing active WorkItem or durably claims the next ready item, creates or recovers the exact matching Goal, resumes the persisted AgentRun prefix, and returns its current fenced lease. Queue and runtime artifacts remain separate; partial runtime failure leaves a recoverable active claim, repeated same-owner calls are idempotent, and no Tool, external effect, queue completion, or cross-store transaction is added.
- Gate 8's first priority/fairness selector remains pure and store-free: `SchedulerPrioritySelector` selects from a complete bounded admission-ordered ready-candidate list with `NORMAL`/`EXPEDITED` priority, oldest-ready tie-breaking, and a bounded expedited burst that forces ready normal work after exhaustion. The non-reserved `SingleWorkerSchedulerQueue.claimNext` path now supplies every dependency-ready candidate and adopts the selected active identity plus next fairness progress; the durable wrapper persists both in one transition before exposure. Recovery still consumes an exact one-shot preference first without changing progress. No admission priority input or authority is added.
- Gate 8 execution acknowledgement is not queue completion: fence-checked `EXECUTING -> AWAITING_VERIFICATION` releases the lease only. The Scheduler queue records a terminal `WorkItemDisposition`: `completeActiveVerified` enters the dependency-satisfaction set `completedWorkItemIds`, while `failActive` enters a separate `failedWorkItemIds` set that never satisfies dependents, so failed work leaves dependents blocked with the cause held in the runtime/RunRecord. The queue stays active through verification and each terminal disposition then releases the slot; the schema-v3 partition is `pending + active + verified + failed` over the same exact admission history, and the disposition persists with exact restart recovery.
- Gate 8 RunRecord-backed result-path finalization: `DurableAgentRunFinalizer` separates RunRecord-backed attempt-result recording from terminal queue disposition. A Verified result completes the Goal; a non-Verified result fails the attempt and parks at `RETRY_PENDING`. Its event-aware construction records one deterministic `VERIFICATION_RECORDED` fact only after the Result transition and one separate `WORK_ITEM_TERMINATED` fact only after the queue's matching terminal partition is durable. Verification identity derives from the retained Result message and RunRecord; termination identity derives from the queue/WorkItem/disposition terminal fact rather than the mutable whole-queue revision. A source without a retained timestamp proposes an injected post-source time, while recorder re-entry for the same identity recovers the first persisted occurrence and still exact-validates every other field. Queue mutation is derived only from terminal Goal state, with no disposition for `ACTIVE` or `RETRY_PENDING` and terminal failure requiring a persisted refused retry decision. It resolves but never persists the RunRecord, binds task plus source document, fails closed while recoverable, and re-claims recovery-requeued work only when applying a terminal disposition.
- Gate 8's retry-aware durable worker: `DurableAgentRunWorker.runOneCycle` drives cycle intent -> claim/lease -> exact Goal-ledger creation/recovery -> RunRecord reference -> cleanup -> execution acknowledgement -> attempt-result recording. Verified completion disposes the queue and clears intent. A failed attempt stops at `RETRY_PENDING`, records or replays the controller decision, then either abandons to one failed queue disposition or checkpoints a replacement AgentRun identity before append and continues through the same fenced path while the WorkItem stays active. Schema-v2 `PendingFinalization` distinguishes the current reference from the replacement phase, so recovery before/after decision, checkpoint, append, rollover, and reference persistence is idempotent. `AgentLoopAgentRunExecution` and `ProcessIsolatedAgentRunExecution` remain the in-process and child-process ports; `processIsolated` selects the real child launcher, explicit retry policy and ledger store, and shared queue/finalizer composition.
- Gate 8's first state-version migration boundary is the lossless pending-finalization schema-v1-to-v2 mapping: retain Goal, AgentRun, and optional RunRecord reference and set the newly introduced replacement AgentRun identity to absent. `FileSystemPendingFinalizationStore.migrateSchemaV1ToCurrent` and the separate stopped-Scheduler `scheduler-migrate-cycle-checkpoint` command validate the complete old artifact, return typed absent/already-current/migrated outcomes, prepare and reread a same-directory v2 candidate, refuse source drift, and atomically replace only after candidate validation; every earlier failure leaves the original bytes authoritative. Ordinary resolution and execution remain fail-closed, and queue, runtime, and external-effect v1 formats require separate information-recovery policies.
- Gate 8 supported submission entry point: `scheduler-submit` takes every store root, identity, occurrence time, queue bound, capability, target, and digest explicitly; resolves the governed active task; captures its repository-memory snapshot at that time; persists the manifest; and admits the exact dependency-free work. It reports bounded `ADMITTED` or exact-replay `REPLAYED` status and invokes no worker, Tool, evidence, RunRecord, cycle, or polling behavior.
- Gate 8 generated-input submission reuses the immutable submission manifest rather than adding a second invocation manifest: one caller-retained canonical submission UUID is the stable replay/message key, other identities derive through versioned domain separation, first use persists the generated occurrence time and exact envelope before queue creation, and replay resolves that manifest before consulting a clock or recapturing repository context. It remains separate from cycle execution and polling; requested priority must join caller-owned intent only after manifest schema v2 persists it.
- Gate 8 supported recovery entry point: `scheduler-cycle` takes explicit project, queue, runtime, ledger, checkpoint, evidence, RunRecord, and invocation roots plus queue/owner identities and bounded retry/lease/timeout policy. It recovers an existing queue and invokes exactly one real `processIsolated` cycle, reporting bounded `IDLE`, `VERIFIED_COMPLETED`, or `FAILED` status with a Scheduler-specific terminal-failure exit. It creates no queue or work, polls nothing, and remains separate from `scheduler-submit`; neither command adds a bus journal, external adapter, or whole-gate promotion.
- Gate 8's bounded foreground drain uses `ForegroundSchedulerDrain` and a separate `scheduler-drain` command to consume that one-cycle boundary over one existing queue. An explicit limit of at most 4096 sequential cycles permits continuation only after verified completion and returns typed idle, failed, or limit stop data with cycle/completion/failure counts, without sleeping, waiting, polling for future work, creating a queue, admitting work, merging submission with execution, applying controls, or adding a drain-progress store. Queue disposition and the existing per-cycle checkpoint remain the recovery authorities.
- Gate 8's bounded Scheduler service contract uses caller-driven `BoundedSchedulerService` over the same durable one-cycle worker. A finite policy caps total and consecutive-idle cycles at 4096 and idle waits at one hour; the service checks a caller-owned stop signal before each sequential cycle, waits only between bounded idle results, resets idle progress after verified work, stops on the first failure, and restores interruption before returning typed counts and a stop reason. The separate foreground `scheduler-service` command is its supported consumer: it reuses every explicit one-cycle recovery input, uses invoking-thread interruption as the local stop signal, and has named real-filesystem cycle-intent restart and expired-lease reclaim evidence. It creates no thread, daemon, supervisor, durable service progress, authenticated control, external adapter, or new recovery authority; durable/supervised background lifecycle and broader orphan reclamation remain separate work.
- Gate 8 runtime events are Goal-bound derived durable facts, never transition authority. The implemented immutable v1 value exposes the finite retry decision/start, stagnation, timeout, cancellation request/application, verification, and terminal-disposition taxonomy with sealed details, exact WorkItem/Goal/AgentRun plus task/snapshot/run/correlation provenance, and bounded authoritative references. Deterministic identities feed a bounded 4096-event per-Goal `RuntimeEventStream`; `FileSystemRuntimeEventStore` exact-replays without rewrite and atomically persists a strict-UTF-8 integrity envelope while rejecting changed identity, foreign binding, prefix rewrite, overflow, corruption, unsupported schema, and symbolic roots. `RuntimeEventRecorder` appends or exact-replays before invoking a publisher port with only `runtime-event/<goal>/<event>` and can recover the first persisted occurrence for a stable identity without weakening exact-content validation. Event-aware retry decision and replacement start, Control admission, authenticated cancellation application, Result finalization with separate verification, Tool/process/lease timeout facts, stagnation, and terminal queue disposition are the first ten implemented transition-owner connections. `FileSystemRuntimeEventPublisher` is the first concrete port adapter: it atomically point-persists only the opaque reference under a deterministic SHA-256 name, bounds capacity, exact-replays before capacity evaluation, and rejects corrupt or foreign reuse. Its first supported composition is the optional all-or-none `scheduler-receive-control` event-store root, publication root, and capacity group, which publishes only `CANCELLATION_REQUEST_RECORDED` after durable request and event persistence and before spool acknowledgement; omitted configuration preserves request-only behavior, and retained-prefix replay repairs publication without another request/event revision. AgentRuntime schema v4 retains lease-timeout and cancellation sources before their derived events; replay repairs publication after later progress without changing source revisions. `PAUSE`/`RESUME`, broader authenticated interfaces, consumers, other-owner and Scheduler composition, and four-kind MessageEnvelope evolution remain absent.
- The first Gate 12 application sub-path uses a trusted `ControlRequestAuthorizer` port over an exact retained `CANCEL` request; envelope metadata never authenticates. AgentRuntime schema v4 atomically retains one authorization-bound `CancellationApplicationRecord` with terminal Goal/current-AgentRun cancellation before event-aware `CANCELLATION_APPLIED` recording. Exact retained-record replay repairs publication without reauthorization. Process signalling, queue disposition, Tool/effect cancellation, credentials/interfaces, `PAUSE`/`RESUME`, and concrete event transport remain separate.
- Remaining connections are dependency-ordered rather than implicitly complete: a supported durable message-bus-to-worker entry point jointly owned by Gates 7 and 8; broader authenticated controls and interfaces; production external adapters and their Gate 11 controls; and Gate 13 background/supervisor plus typed handoff/multi-agent execution. Gate 7 owns delivery/transport, Gate 8 runtime/recovery, Gate 11 Tool execution controls, Gate 12 authenticated controls, and Gate 13 concurrency. General orphan inventory/cleanup is not implied by point recovery and requires a separate bounded retention and authority decision.
- Gate 8 Scheduler delivery is at-least-once rather than universally exactly-once. Stable idempotency keys, fenced leases, checkpoint/recovery, versioned state migration, orphan reclamation, and replay-safe or compensatable effects compose near-exactly-once user-visible behavior; stale fences fail closed and every effect outcome remains explicit.
- The graph projection contract types five node kinds and six endpoint-checked edge kinds (JUSTIFIED_BY, SUPERSEDES, DEPENDS_ON, MODIFIES, VERIFIED_BY, RECORDED_AS) over the Decision/Architecture/Dependency/Task/Execution domains with element provenance and derived rebuild status, keyed to one snapshot identity; `TaskImpactQuery` answers the task-to-decision-to-code-to-test chain with snapshot-traceable immutable results, and transitive DEPENDS_ON closure is deferred by decision.
- The Gate 6 run-evidence production path: `RunEvidenceGraphProducer` projects evidence-only task/artifact/execution nodes and one RECORDED_AS edge from one snapshot and one task-matched stored run record, with observation states mapped one-to-one to element freshness; it never emits edges no evidence justifies.
- Workspace RunRecord observation is bounded to the 256 most recent filesystem records; full listing and point replay remain intact, selected corrupt records stay explicitly unavailable, and no retention deletion is implied.
- The Gate 6 production graph composition: the CLI `run` path observes a 256-record recent execution window, the run's target file, safe Git index/untracked/deleted metadata, and an explicit unavailable tracked-worktree diff; it merges accepted decisions and explicit justification edges and reports bounded graph/impact counts. Inputs are preflighted before execution, and post-persist reporting cannot change the durable run exit code.
- CLI graph inputs available before execution are preflighted before evidence creation; duplicate document/target paths collapse to one target-preferred artifact. Once a finalized RunRecord is persisted, reconstructible Project Brain reporting is degradable and cannot change its durable exit code.
- Production text limits are Unicode-safe at their prefix/suffix boundary, so valid supplementary characters cannot become malformed persisted or displayed text. Governed content and artifact reads enforce byte ceilings during streaming and consume at most one overflow-detection byte after the limit; metadata size checks remain early diagnostics rather than the resource boundary.
- External command authority exists in exactly two places, each user-granted and decision-scoped: `GitWorkspaceCollector` (a configured external program) and `IsolatedWorkerLauncher` (the current JVM only).
- `GitWorkspaceCollector` is scoped to one fixed filter-free `ls-files` metadata invocation through a canonical absolute executable outside the observed project, no shell or inherited `GIT_*` overrides, project-confined discovery, watchdog timeout, and digest-only retention. Tracked worktree diff is explicitly UNAVAILABLE because verified Git comparison commands can execute required clean filters. The authority-boundary exit criterion is pinned by `WorkspaceAuthorityBoundaryIntegrationTest`; diagnostics/terminal/selection adapters remain owned by later gates.
- In-process Tool execution now has a process-wide 64-live-worker isolation ceiling: a slot remains occupied until the real daemon thread exits, and saturation fails closed with typed terminal evidence before thread creation. This prevents unbounded accumulation but cannot terminate stuck code; process isolation remains required for long-running Scheduler Tool workers. Parent-directory fsync for power-loss durability remains separately scoped architecture work.
- Runtime package dependencies are now acyclic: neutral verification decision/status/code values live in `kernel`, AgentRun finalization lives in `application`, and the enforced direction is application -> run/verification/loop/kernel, run -> loop/kernel, verification -> loop/kernel, loop -> kernel. RunRecord schema and enum names are unchanged; the project remains one Gradle module.
- The long-term OS substrate is Workspace and Project Brain -> Event/Message Bus with IPC adapters -> Agent Runtime and Scheduler -> MCP/Model Gateway -> Skill Engine and Plugin Marketplace.
- Runtime Agents communicate by typed messages rather than direct Agent-to-Agent calls once the bus boundary exists.
- Agent orchestration escalates from one worker to sequential work and only later to Producer-Reviewer, bounded fan-out/fan-in, supervisor allocation, or shallow hierarchy; one Kernel coordinator owns terminal run state.
- Every worker handoff preserves the approved task revision, common immutable Workspace snapshot, authorization, correlation, causation, budgets, and artifact or evidence references. Heartbeats and quality signals are diagnostic only.
- MCP is a core server/client interoperability layer for governed Tools, resources, Workspace views, and memory.
- Repository instructions, Tool/terminal output, model responses, MCP content, plugins, dependencies, and generated artifacts are untrusted data. Architecture owns the common provenance, secret/outbound-data, least-privilege, isolation, audit, and rollback baseline; Gates 9, 11, 12, 14, and 16 own concrete enforcement for their surfaces.
- Interfaces share one Run, approval, verification, evidence, control, recovery, and change-review API. Delivery order is API first, CLI reference surface, VS Code for in-context work, and Desktop later for supervision; the primary UX presents plan, files/diff, tests/evidence, risks, approvals, recovery, and commit readiness rather than Agent topology.
- Product milestones are V1 AI Development Experience, V2 AI Development Platform, and V3 AI Operating System; they do not replace maturity gates.
- Product milestones describe outcomes; dependency-ordered Delivery Gates may build platform foundations before every V1 interface is polished.
- Self-hosting development of Enhancer and local or hybrid model execution are separate capabilities; neither implies the other.
- Git and canonical documents remain authoritative while Project Brain supplies rebuildable Decision, Architecture, Dependency, Task, and Execution graph projections.
- Agent plugins, Skills, Tools, and workflows are separate extension types; marketplace installation never grants execution authority.
- The future Model Router defaults sensitive code to approved local models and requires policy authority for remote transmission.
- New contracts must name their current or next-gate integration consumer.
- `FileSpoolMessageTransport` is the first `MessageTransport`: it writes one encoded route plus envelope to its own file under a configured spool directory a peer reads. Durably spooled is `ACCEPTED`, capacity exhaustion against a `BackpressurePolicy` is `BACKPRESSURED`, an unusable root is `UNAVAILABLE`, and a refusal spools nothing. Its concrete referenced-send result returns the accepted canonical point filename while leaving `MessageTransport` and `TransportOutcome` unchanged. It promises no ordering across messages and is one-directional per instance; connection 3d composes separate work and result instances. `scheduler-spool-work` derives one governed Work envelope and returns that point reference; the separately invoked Work point receiver reads and acknowledges it after durable admission.
